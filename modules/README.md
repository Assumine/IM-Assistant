# 助手能力包

能力包统一放modules/<module-id>/。当前基座为完整OpenCode应用，优先使用其服务端、GUI、RPC和命令扩展；缺口才做有限产品补丁，不再以旧Python SDK清单作为每个包的强制前置框架。

整体保持核心框架＋插件。插件可包含完整业务、界面和后端，但只经核心公共接口与展示位置接入；不能覆盖全局发送/队列、私读其他插件数据库或让无关插件依赖自己启动。运行时、SDK、驱动等属于依赖，不能混作功能插件。需要公共入口时补框架位置，而不是把插件业务搬入核心。

一个包可以承载完整能力及独立服务，不为原生上下文、压缩和工具循环分别创建必装插件。QQ转发、Codex整套原生适配及后续研究/设备/下载等按任务接回；重负载与原生会话故障隔离。

`codex-native`已通过R3-01隔离可行性验收，提供原生主界面入口、跨进程生命周期和显式下次启停，默认关闭，生产账号与安装包未验收。`qq-portal`正在实现R3-02：已隔离验证结构化入口、来源去重/绑定、普通Session/整套后端的显式目标、普通Session待办追加、当前输入护栏续接和已结束输入的关联后续、Codex当前任务引用的原生轮次校验和已结束输入的关联后续，以及不改变当前绑定的跨会话一次确认控制接口；可按完整目标和原生输入反查QQ起始消息，不用当前绑定猜收件人。Codex输入不创建OpenCode影子Session/Inbox。显式授权的控制层已接列表、绑定、队列/状态读取及固定输入撤回，写命令按原消息冻结目标、保存历史回执且不重放。目录/队列清单已支持确认发布后的引用序号选择，绑定固定完整目标，撤回固定原生输入ID。实际QQ、确认交互、外发、未引用清单的序号与其余控制命令仍未接通；Codex待办追加仍受原生接口限制。两者都不接管原生执行队列。主程序不得依赖QQ登录、业务网关或任一模块启动成功；这些切片不代表业务模块已全部正式迁入。
