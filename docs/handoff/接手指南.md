# 新接手 AI 的起步说明

本仓库已经完成地基重构的设计与目录准备，尚未实现新版宿主或完整会话后端。接手目标是按明确任务建设地基，保留“整套后端接入”边界，业务模块迁移另做。

## 1 先读哪些内容

按以下顺序读取即可开始，不必先寻找旧应用或复盘整个聊天历史：

1. 仓库根目录 [AGENTS.md](../../AGENTS.md)，了解不可改变的范围与开发约定。
2. [进度记录](progress.json) 和 [任务分解](work-plan.json)，确定实际已完成内容和下一任务。
3. [基础实现约定](../architecture/基础实现约定.md)，按已确定默认值实现，不重新设计第二套协议。
4. 当前任务关联的 [接口契约](../architecture/接口契约.md)、Schema 和 [验收用例](../architecture/实施与验收.md)。

[完整方案](../architecture/重构方案.md) 用于判断职责边界；[决策与外部前提](决策与外部前提.md) 说明哪些是已接受决策，哪些要到后续阶段再核实。

## 2 新克隆后的第一组命令

仓库使用 Python 3.12 或更高版本，当前设计校验依赖只有 `requirements-dev.txt` 中的 jsonschema。

```sh
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe tools/next_task.py
.\.venv\Scripts\python.exe tools/validate_design.py
```

以上为 Windows 下无需激活的写法，其他系统将环境内解释器换为 `./.venv/bin/python`。后续示例中的 `python` 均指这个环境的解释器。不要因为运行命令方便，把旧应用的虚拟环境路径写进项目源码。

当前 `next_task.py` 应报告 `P0-01`。设计校验通过只证明文档、Schema、示例与任务定义一致，不代表地基已经可运行。

## 3 接到继续开发指令后怎么做

读取 `next_task.py` 返回的第一个可开展任务，再在 `work-plan.json` 找到它的依赖、目标文件、输出要求、验收编号与测试文件。目标文件是待创建的实现位置，不代表它已经存在。

先把当前任务记为 `in_progress`，然后完成对应实现及有意义的行为测试。保持工作范围在该任务及其必需依赖内，不能为了消除测试失败改成另一个架构。依赖的任务未完成时，先处理依赖。

验证命令为：

```sh
python tools/validate_design.py
python tools/run_runtime_checks.py --task P0-01
```

把 `P0-01` 换成当前任务编号。运行测试文件尚未创建、没有测试或导入失败，都不能算通过。工具不会自动把任务标为完成。

测试工具的 blocked 表示目前无法确认验收，不会修改任务状态。尚未实现的任务仍然是可开展的 pending，不能因此误判为需要外部资料才能继续。

任务完成后，更新 `progress.json` 的状态、实际产物和验证记录，并在 [最近交接](最近交接.md) 记录本轮结果及下一步。验证摘要只记命令、测试数量、结果和限制；不要提交模型原文、账号、凭据或私人会话。

如果用户要求持续推进，可以在满足依赖和验收后继续下一个任务，不必每项询问许可。会话结束前必须留下准确进度；不得仅为了交接方便把未完成项改成 done。

## 4 当前第一项工作

`P0-01` 创建 Python 侧契约类型、错误模型及静态清单验证，使用当前 JSON Schema 作为结构依据。至少覆盖：无执行的静态清单读取、必需方法缺失、协议版本不兼容、字段与路径错误。

预期新增文件：`sdk/__init__.py`、`sdk/contracts.py`、`sdk/errors.py`、`sdk/manifest.py`、`tests/__init__.py`、`tests/test_contracts.py`。同时处理决策记录中归属 P0-01 的未决契约细节，保持类型、Schema、文档和行为测试一致。不启动 OpenCode、不安装 QQ、不接研究模块、不创建宿主业务调度器。

当前应失败的行为验收命令是 `python tools/run_runtime_checks.py --task P0-01`，原因应为测试文件尚不存在。实现第一任务后，这条命令才应真实通过；不得删除缺失文件保护或返回固定成功来达标。

## 5 怎样使用旧项目和公开依赖

旧客户端源码继续保留在本地，不上传 GitHub。仓库根目录的 `handoff.local.json` 提供只读定位信息，文件被 Git 忽略；[本地配置示例](../../handoff.local.example.json) 用于换机器时重新设置。`next_task.py` 会检查源码入口是否存在并显示可参考的本地目录，不读取源码内容或私人数据。

配置指向旧项目的 management_center 目录。可参考原窗口入口、静态页面、会话控制器和历史加载文件；只读参考不授予启动旧服务、修改旧源码、清理旧任务或上传整个目录的权限。P0、P1 和使用隔离上游的 P2 不需要这些旧路径，也不需要原用户的账号。

OpenCode 参考后端的历史依赖基线位于 [依赖基线](dependency-baseline.json)。P2 才建立后端自己的包文件和锁文件，先核对公开包的实际类型与运行要求。不要在 P0 提前引入整个 Node 依赖树，或假定原用户机器已有的网关、端口和文件在别处存在。

本机已配置可用的旧客户端参考目录。其他机器缺少配置时，只影响 P3 的真实旧页面集成；协议、夹具与其他独立任务继续推进。P3 使用本地源码核对原样式与交互，不要求先把源码上传到 GitHub；需要纳入新实现的文件必须另行检查范围与依赖，不能搬入原私人配置、数据库和浏览器资料。

## 6 遇到模糊或冲突时

同一轮最新明确用户要求优先，其次是当前仓库的已接受决策、接口规范和任务定义。源码中的占位内容、旧实现和外部后端示例不能覆盖这些边界。

可逆的普通实现选择可以采用基础实现约定并记录理由。改变接入单位、队列所有权、生产数据所有权或正式切换范围时，应先说明具体冲突并获得明确方向，不能在底层悄悄改掉方案。

遇到外部前提缺失时记录为 blocked，说明缺什么、影响哪些工作和哪些工作仍可继续。不要把一个后端或原生 UI 的阻塞扩大成整个项目不能启动。

## 7 结束本轮时必须留下什么

- 修改了哪些实现和公开契约。
- 当前任务状态及真正完成的产物。
- 实际执行的命令、测试数与结果，未运行部分单独注明。
- 现有阻塞、尚未核实的上游能力和下一项任务。
- 发生架构偏离时的理由；不能用补丁或新的硬编码入口隐藏偏离。

提交前检查 Git 差异，只提交源码、公开文档和合成测试。`runtime/`、`.reports/`、账号、模型请求日志和下载产物保持本机保存。
