## 本轮实施与归属

qq-portal新增confirmation.ts，只通过原公共插件KV保存跨会话确认提案和不可变选择。提案含来源信封、稳定ID、摘要、原绑定/目标和父输入ID，不存正文、执行状态或第二条任务队列。receive为原路由函数的内部提取，确认后继续同一个原生append/continue/send链路，不复制路由器或重新调度。原生Session/Inbox及Codex仍拥有执行、待办、历史、上下文和压缩。

首次跨会话引用返回confirmation-required、confirmationID、原Target和duplicate=false。并发重投只保留一份提案，之后duplicate=true；未来外发需据此去重提示。未同意前不查执行器、不发输入、不改绑定。提案跨重绑、取消绑定和重启保持原目标，不按新绑定改路由。

confirm(originalRaw, { confirmationID, scope, actorID, choice })是可信宿主控制API。未来认证传输必须先收到明确用户选择，并按原消息ID取得原始事件；不可让模型工具或普通正文直接调用。该接口重做当前权限检查、核对原成员/范围和完整内容/引用摘要；消息或附件丢失不能由摘要猜造。choice为原子首写的approve/decline，取消不能后来自动变同意。已批准后从原目标继续，binding不变，原生队列仍唯一。确认本身不代表原生接纳或任务执行完成。

重复确认经已有来源ID和原生回执核对；失回执/unknown不重发。同意记录不是接纳事实：若同意后中断且没有origin，同一原消息再次到达时可沿来源原子首写路径移交一次；origin已存在的未知结果只能核对。不能缓存正文并后台自建待执行队列。撤回待确认原消息后不能再确认；确认/补充的撤回也不取消父任务。若原任务已经结束、归属失效或原生只读查询失败，沿用原有blocked/uncertain，不因用户同意而绕开原生护栏。一次跨会话同意也不是订阅整条会话的全部通知。

此前普通Session待办append/当前输入护栏、Codex当前轮次引用及来源反查已经补齐，未改这些状态所有者。Codex待办追加仍缺原生原子追加/CAS，不能用本地锁＋整条update覆盖其他客户端。已结束任务的关联后续仍待实现；历史不可读或任意409/unknown不是新建任务的证据。实际QQ确认提示/按钮/指令、OneBot连接和外发尚未装配。
