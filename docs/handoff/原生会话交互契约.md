# 原生会话交互契约（R2-01）

基于锁定的 OpenCode v2.2.3，应用仍为核心框架＋插件。R1 已把原生桌面和网页会话接入助手隔离配置；本阶段核对裁剪后的交互闭环，不能再加一层发送或排队控制器。

## 状态归属

| 行为 | 唯一原生所有者 | 后续接入限制 |
| --- | --- | --- |
| 草稿捕获、清空、失败恢复 | `app/src/composer/submission-state.ts`、`submit.ts` | 不把晚到的失败恢复写进新选中的会话 |
| 接收回执、乐观待发送、HTTP/SSE 对账 | `client/src/solid/data.ts` | 同一原生消息 ID 重试；第一次接纳的载荷有效，不能换 ID 盲目重发 |
| 待办真相与持久化 | `core/src/session/inbox.ts`＋原生 SQLite | 不建立桌面队列、QQ 队列或另一张权威任务表 |
| 运行、安全步骤引导、续排 | 原生 Session / run coordinator | 页面选择、回复通知、QQ 是否在线不得决定执行是否继续 |
| 队列编辑、撤回、顺序 | `app/src/session/composer/queue.ts` | 原生重排采用接纳替代项后撤销旧项；失败须对账，不改成客户端假顺序 |
| 会话切换、历史、分页锚点 | `session-resolution.ts`、timeline model/interaction/virtualizer、原生 client store | 不加第二套最近消息缓存或按 DOM 到达时间排序 |
| 展示和流式文字动效 | 原生 session-ui / markdown | 初次历史和切回历史不带 `data-markdown-enter`；助手消息弹入主题留到 R4-02，不能提前搬旧动效控制器 |

## 已核实的交互

- 空闲输入在 HTTP 接纳之前出现在原生待发送时间线；忙碌时的独立输入立即进入原生队列，不先冒充已交付消息。只有正在执行的一项时不出现空队列面板。
- 入队、撤回和查看其他会话在模型首个 token 尚未返回时即可完成，不以第一条 AI 回复作为触发器。
- 引导在原生安全步骤消耗，优先于后面的独立排队输入。撤回待办不会撤销此前任务，也不把撤回内容发给模型。
- 原生 drain 会连续处理队列，不在每个排队输入之间发布一次空闲。上一条 assistant 的完成早于下一条 user 的交付；队列耗尽才写 idle。不得为复制旧回执逻辑强行插入“空闲→运行”的跳变。
- 选中另一会话、回到原会话、刷新和重新订阅不改变待办归属或重复发送。未发送草稿也保持各自归属。
- 采用原生历史顺序和分页锚点。完成的历史文本在分页、切回时不重播流式文字动画。

## 验收入口与边界

`python tools/run_runtime_checks.py --task R2-01` 执行：

1. 原始源码与累计补丁清单核对。
2. 95 项原生 client/store/queue/list/草稿恢复/会话解析/历史投影测试。
3. 本地可控模型＋真实助手 HTTP/SQLite：首 token 前接纳、去重、撤回、安全步骤引导、连续续排、空闲再次输入、服务重启不重做。没有调用外部模型。
4. 生产构建 Chromium 队列与历史 keeper 47 项；其中新增 2 项在助手无项目模式下检查未确认请求跨会话和刷新、空闲发送无虚假队列；已有分页恢复用例增加无项目模式和历史动效断言。
5. 新增 2 项各重复 10 次、5 workers、无重试、完全并行，排除共享场景状态。
6. 原生 `bun run check`。
7. 原生 Markdown 组件 keeper：初始文本无动画，新到达的 `again` 仅标记一次，完成后重新挂载不重播；重复 10 次、2 workers、无重试。该验收入口同时修复了上游 stories 命令未引用带空格目录导致 Windows 无法启动的问题。

浏览器 keeper 使用原生应用＋HTTP/SSE fixture，真实后端另由第 3 项覆盖，不能声称浏览器用例连接了真实外部模型。此阶段不新增消息弹入效果、不验收换肤或安装包、不切换旧生产软件。

独立的 `bun run typecheck:e2e` 仍失败，有 14 条诊断；临时恢复本轮前两份 keeper 源码后重查，诊断与前一提交逐条相同，本轮新增 0 条。该检查不能记为通过；未改变文件中的旧 fixture 类型债务留在 R5 全量验收前处理。原生 `bun run check` 的 36 项成功不能替代这份单独结果。

## 为什么不新增 conversation-profile 控制代码

原计划预留的 `packages/im-assistant/src/conversation-profile.ts` 在接入后已没有独立职责：R1 的 profile/运行策略负责宿主边界，原生会话组件和 store 已完整负责交互。为了凑文件而包一层会话配置、缓存或状态机会再次偏离整体架构。因此把该输出改为本契约、真实后端验收和原生 keeper 回归；产品交互控制器维持上游实现。

后续 R2-02 核对原生上下文、压缩和用量；Codex 同级后端适配属于 R3-01，QQ 可选转发属于 R3-02。两者都必须沿本表的唯一状态归属接入。

## QQ受控图片接纳

图片与文字保持同一原输入ID，经原生prompt/Inbox或整套后端queue接纳，图片不成为另一项排队任务。原生blob/native线程负责存储，QQ仅做授权、平台取图、摘要与结果引用。静态配置明确开启后才取图；重复、失效图片和能力关闭都有不可改绑复活的原始事实。原生文本补充接口缺附件参数时明确拒绝整条含图消息，不擅自改为新任务，也不在插件里改写私有Inbox。Codex已有的原生image参数通过通用后端契约使用，其队列文字替换不得丢失附件。
